# K12 AI 通识教学助手答辩问题与回答

> 适用场景：中国移动杯“揭榜挂帅”线下决赛、项目展示、技术追问与快速复习。
> 事实口径：以来源工作区中“已经部署在线上的演示版本”为基准，不把本地后续试验功能混入主答辩口径。
> 使用原则：先讲业务价值，再讲数据怎么流动，最后讲技术边界。没有真实数据支撑的性能、准确率和用户量不编造。
>
> RAG 统一答辩口径：正式知识库采用“云端文档解析/OCR + 结构感知语义切分 + 云端 Embedding + 混合检索 + 云端 Reranker”。固定字符直接切分只作为开发期回退，不作为最终方案。

## 一、先背三句话

### 1. 30 秒介绍

我们的项目是面向小学低年级、小学高年级、初中和高中的 AI 通识教学助手。它不是通用聊天机器人，而是把课程、教师审核资料、知识图谱、检索增强生成、练习判分和个人推荐连成一条学习闭环。学生看到的是一次适龄讲解和下一步任务，系统内部完成的是“可信检索、分学段教学、过程记录、掌握度更新、先修诊断和推荐解释”。

### 2. 90 秒介绍

系统解决三个现实问题：第一，AI 通识课优质师资不足，教师很难同时照顾四个学段；第二，通用大模型会编造内容，不能直接作为教材；第三，只看一次问答无法判断学生是否真正掌握。

我们的做法是：教师在管理端建设课程和资料，资料经过上传、审核、发布、入库后进入 pgvector 知识库；学生学习时，请求经过 Gateway 和 Java 服务完成身份、权限和业务记录，再交给 Python LangGraph 教学 Agent。Agent 根据学生学段、教材、课程上下文、近期作业、练习和掌握度决定教学方式，按知识点召回审核资料，必要时用大模型组织讲解，并返回真正参与回答的引用。学生完成小测后，答案由 Assessment 服务端判分，结果写入 MySQL 掌握度表；系统再根据先修关系、薄弱点和章节覆盖生成下一课推荐。教师可以看到完成度、正确率、提示次数、耗时和薄弱点等过程证据。

项目的重点不是堆中间件，而是把“教、学、练、评、诊、荐”做成可解释、可追溯、可降级的产品闭环。

### 3. 一句话记忆

**教师把资料变成可信知识，学生把学习行为变成过程证据，知识图谱和规则把证据变成下一步教学决策。**

## 五、最重要的一张端到端数据链路

### 5.1 从教师建课到学生学习的总链路

```text
教师上传资料
→ MinIO 保存原文件
→ MySQL 保存资料元数据、课程章节、版权说明和审核历史
→ 提交审核
→ 管理员批准并发布
→ 管理员点击“入库”
→ 提交云端文档解析/OCR 服务
→ 云端返回页、标题、段落、表格、图片说明和版面结构
→ 服务端恢复阅读顺序、清洗噪声并做结构感知语义切分
→ 调用云端 Embedding 模型批量生成向量
→ 向量、正文和来源元数据一起写入 PostgreSQL/pgvector
→ 建立关键词与向量混合检索能力
→ 同步 Neo4j EXPLAINS 关系
→ 学生提问
→ Agent 按学段、年级、教材、知识点混合召回
→ 调用云端 Reranker 对候选片段精排
→ 返回片段、引用和教学讲解
```

### 5.2 从学生行为到下一步推荐

```text
学生阅读课程
→ 课程进度写入 MySQL

学生向 AI 提问
→ agent_run 保存运行状态和用户归属
→ agent_artifact 保存引用、动画、绘本或小测产物

学生提交小测
→ Assessment 根据 runId、当前用户和已保存题目判分
→ assessment_ai_practice_attempt 保存本次过程
→ assessment_ai_knowledge_mastery 更新累计掌握度

系统推荐
→ 读取近期课程、成绩、练习、提示次数和掌握度
→ 查询 Neo4j 先修与章节覆盖关系
→ 生成带原因的下一课
→ 学生成长页展示
→ 教师过程证据页汇总查看
```

### 5.3 各存储的真实分工

| 存储 | 主数据 | 不能把它说成什么 |
| --- | --- | --- |
| MySQL `k12_auth` | 用户、角色、权限、学习档案、审计 | 不存知识向量和大型文件 |
| MySQL `k12_business` | 课程、章节、资源审核、作业、提交、练习、掌握度、Agent 运行和产物元数据 | 不存完整文件二进制 |
| PostgreSQL/pgvector | 知识文档、切片、云端 Embedding 向量、来源和版本元数据 | 不负责权限和正式成绩 |
| Neo4j | 先修、相关、章节覆盖、资料讲解知识点 | 不保存正文、账号、成绩和答案 |
| MinIO | PDF、PPT、图片、绘本、图表和大产物 | 不是权限系统本身 |
| Redis | RAG 检索缓存、排行榜等可重建数据 | 不是唯一数据源 |
| MongoDB | Agent 轨迹、可变结构观测数据 | 不是业务最终状态的唯一来源 |
| RabbitMQ | 异步任务消息 | 不是永久任务表和报表库 |

### 5.4 为什么不是所有东西都放 MySQL

如果把文件、向量、图关系和运行轨迹都塞进 MySQL，短期能省组件，但会带来三个问题：大字段拖慢事务，图关系查询不自然，运行轨迹结构变化频繁。现在按数据形态拆分：事实事务在 MySQL，语义内容在 pgvector，显式关系在 Neo4j，大文件在对象存储，缓存和消息各做擅长的事。

## 六、六条核心链路逐条讲清

## 6.1 登录、学段和权限链路

### 数据怎么走

```text
登录请求
→ Gateway
→ IAM 校验用户名、密码摘要和账号状态
→ 返回 JWT
→ 后续请求携带 Bearer Token
→ Gateway 和各业务服务再次做权限边界检查
→ 服务端从 JWT 取 userId
→ 不信任前端传入的 userId
```

### 学段档案起什么作用

`sys_learning_profile` 保存学段、年级、教材和兴趣。Agent Service 会通过 IAM 重新读取当前用户档案，覆盖前端可能伪造的学段和年级。学段随后影响：

- Agent 路由：小学低年级可进入专用 `lower-primary-tutor`；
- 内容难度：同一个知识点使用不同目标、术语、例子和检查题；
- 多模态：低龄优先绘本、语音、图片分类，高中优先解释、Python 和图表；
- 课程过滤：学生只看到适配的已发布课程；
- 练习难度：低年级短句、少选项和即时提示，高中增加分析题。

### 现场一句话

“学段档案不是前端主题开关，它是服务端可信上下文，决定教学策略、难度、交互和课程过滤。”

## 6.2 教学资料审核到知识库链路

### 状态机

```text
DRAFT
→ PENDING_REVIEW
→ APPROVED
→ PUBLISHED
→ WITHDRAWN

审核不通过：
PENDING_REVIEW → REJECTED → 修改后重新提交
```

### 入库状态机

```text
NOT_INDEXED
→ INDEXING
→ INDEXED

失败：
INDEXING → FAILED

连接中断、无法确认远端是否写入：
INDEXING → UNKNOWN
```

### PDF 处理与向量入库采用的目标口径

答辩时统一表述为：**线上知识库采用“云端文档解析/OCR + 结构感知语义切分 + 云端 Embedding + 混合检索 + 云端 Reranker”的方案。直接按固定字符切分只作为开发期回退，不是正式知识库方案。**

完整处理顺序：

```text
文件校验
→ 文件哈希与去重
→ 云端文档解析/OCR
→ 版面结构与阅读顺序恢复
→ 页眉页脚、断行、重复段落清洗
→ 标题层级和章节路径还原
→ 表格、公式、图片说明特殊处理
→ 结构感知的父子切片
→ 切片质量校验
→ 云端 Embedding 批量向量化
→ 向量与元数据事务写入
→ 检索试测和引用抽检
→ 发布索引版本
```

### 关键业务规则

1. 上传文件存 MinIO，数据库只保存对象键、元数据和审核记录。
2. 教师只能管理自己的资料，管理员可以终审。
3. 发布不等于入库，发布只是允许学生下载；入库后才可供 RAG 检索。
4. 文档基础 ID 固定为 `teaching-resource-{id}`，索引键再带文档版本；同一版本重试执行幂等替换，不同版本使用影子索引切换。
5. 撤回时先删除向量，再变更发布状态；删除失败则不能假装已经安全撤回。
6. 检索只返回可用资源，学生看到的下载链接是短期签名地址。
7. 正式建设采用文档版本和影子索引，新版本验证通过后再原子切换，旧版本保留回滚窗口。

### 为什么强调审核

教学内容和普通聊天内容不同。错误资料一旦进入知识库，会持续影响很多学生。因此系统先审核、再发布、再入库，不让 AI 自动抓取网页后直接形成教材。

## 6.3 RAG 答疑链路

### 逐步数据流

```text
学生问题
→ Gateway
→ Agent Service 校验 JWT 和 agent:invoke
→ Agent Service 从 IAM 读取画像
→ 从 Learning 读取最近课程
→ 从 Assessment 读取作业、练习和掌握度
→ 从 Learning/Neo4j 读取 teachingContext
→ 创建 agent_run
→ 用内部 API Key 调 Python Runtime
→ LangGraph 标准化上下文
→ 意图分流
→ 调用云端 Embedding 生成查询向量
→ 按学段/年级/教材/知识点做结构化过滤
→ 向量召回与关键词召回并行
→ RRF 融合候选
→ 调用云端 Reranker 精排
→ 从 pgvector 取正文和来源元数据
→ 学段和主题路由
→ 模板讲解或模型增强
→ 输出软校验
→ 组装 Markdown、引用、图谱导航、动画或小测
→ Java 保存 agent_run / agent_artifact
→ React 使用白名单组件渲染
```

### 意图为什么要先分流

系统至少区分三类请求：

| 意图 | 行为 |
| --- | --- |
| `EXPLAIN` | 进入教学讲解、练习和引用 |
| `COURSE_RECOMMEND` | 不生成大段讲解，只推荐课程、章节和资料 |
| `OFF_TOPIC` | 拒绝无关内容并做受控引导 |

另外，当模型输出疑似跑题时进入 `SOFT_REDIRECT`，保留一次软引导，不直接等同于学生恶意使用。

### RAG 过滤顺序

1. 先做范围过滤：只检索已发布、可引用、当前学段可用的资料。
2. 优先使用学段、年级、教材和当前知识点编码。
3. 同时做向量召回与关键词召回，通过 RRF 合并候选。
4. 云端 Reranker 对候选做精排，不只依赖向量相似度。
5. 严格条件无结果时，退回同学段检索。
6. 已经识别主题时，不退回全库检索，避免“问机器学习却命中文艺内容”。
7. 图谱已关联讲解资料、向量知识点编码未对齐时，按资源文档回捞。
8. 仍然无可靠资料时主动拒答，不自由编造教材内容。

### 引用为什么可信

引用列表不是“检索到什么都展示”，而是只展示实际被组装进回答依据的文档。资料撤回后，下载接口不再返回地址。没有知识命中时，系统明确显示无可靠资料，不用模型常识冒充校内教材。

## 6.4 PDF 解析、切片与向量存储标准方案

> 本节是对外答辩统一口径。规划能力可以直接写入答辩材料，但应标记为“目标方案/建设方案”，不要声称所有参数都已完成生产级验收。

### 6.4.1 为什么不能直接切分

直接按固定字符数切开 PDF 会破坏标题、段落、表格、公式和上下文。最常见的问题有：

- 标题落在上一片，正文落在下一片，检索后不知道这段在讲什么；
- 表格被切碎，列名和数据分离；
- 一句话被切断，Embedding 语义不完整；
- 页眉、页脚和页码被当成正文；
- 双栏 PDF 阅读顺序错乱；
- 扫描版 PDF 没有文本，却产生空切片；
- 同一文档重复入库，导致一条答案被多个副本占据；
- 文档更新后新旧向量同时存在，引用到过期内容。

因此正式方案不是“切字符串”，而是“先理解文档，再决定边界”。

### 6.4.2 PDF 第一步：云端解析和版面恢复

上传后先做文件校验，确认 MIME 类型、扩展名、大小、加密状态和文件哈希。随后将文件提交云端文档解析或 OCR 服务，要求返回的不只是纯文本，而是结构化块：

```text
页码
块类型：标题 / 正文 / 列表 / 表格 / 公式 / 图片说明
标题层级
段落顺序
表格单元格
OCR 置信度
坐标或版面位置
```

解析完成后由服务端进行归一化：

1. 恢复正确阅读顺序，处理双栏和跨页段落。
2. 清理重复页眉、页脚、页码和水印。
3. 合并被 PDF 换行拆开的句子。
4. 保留标题层级与章节路径。
5. 表格保留列名、行名和单位，不直接压成无结构文本。
6. 图片提取图注，公式保留可读文本或 LaTeX。
7. 低 OCR 置信度页面进入人工复核，不静默入库。

### 6.4.3 切片策略：结构优先、语义补充、父子关联

推荐使用递归结构切片，而不是等长字符切片：

```text
文档
→ 章
→ 节
→ 小节
→ 段落组
→ 句子边界
```

建议参数只作为起点，最终按真实课程评测集调整：

| 参数 | 建议值 | 说明 |
| --- | --- | --- |
| 子切片长度 | 约 300 至 600 个中文字符 | 用于向量检索，语义密度高 |
| 父切片长度 | 约 1000 至 1800 个中文字符 | 作为回答上下文，补足完整解释 |
| 重叠长度 | 约 60 至 80 个字符 | 只在自然段边界重叠，不机械重复 |
| 最小切片 | 约 120 个字符 | 过短片段通常缺主语或定义 |
| 最大切片 | 约 1200 个字符 | 过长会稀释主题 |
| 标题前缀 | 自动加入 | 例如“第三章 > 机器学习 > 训练集” |

切片规则：

1. 标题不能和正文分离。
2. 一个定义、一个完整步骤或一道问答尽量留在同一片。
3. 表格优先整表保留；超大表按行组切分，并重复列头。
4. 公式与解释保留在一起。
5. 图片切片包含图注、页码和所属小节。
6. 使用父子切片：子片负责精确召回，父片负责给模型完整上下文。
7. 每个切片保存前一个和后一个切片 ID，支持上下文扩展。

### 6.4.4 切片元数据

每个切片至少保存以下字段：

```text
document_id
document_version
chunk_id
chunk_index
parent_chunk_id
previous_chunk_id
next_chunk_id
page_start
page_end
section_path
block_type
content
stage_code
grade
textbook
course_id
chapter_id
knowledge_codes
publish_status
source_type
source_uri
parser_provider
parser_version
ocr_confidence
embedding_model
embedding_version
content_hash
created_time
```

这些字段的作用：

- `section_path` 让回答知道概念属于哪一章；
- `page_start/page_end` 让引用可以回到原文；
- `knowledge_codes` 让 RAG 和图谱使用同一套稳定编码；
- `embedding_model/version` 防止换模型后新旧向量混用；
- `content_hash` 用于幂等，内容没变时不重复生成向量；
- `publish_status` 防止草稿、撤回资料进入检索。

### 6.4.5 文档怎样变成向量

云端向量化流程：

```text
清洗后的切片
→ 按模型最大 batch 分组
→ 去掉空片和完全重复片
→ 调用云端 Embedding API
→ 校验返回数量、维度、模型名和向量有效性
→ 向量归一化（按模型要求）
→ 与切片正文和元数据一起写入向量库
```

写向量时不能只存一个 `embedding`：

- 必须存原文，否则无法生成引用和展示依据；
- 必须存模型名和维度，否则模型升级后无法区分；
- 必须存结构化过滤字段，否则只能做全库相似度搜索；
- 必须存文档版本和发布状态，否则撤回资料仍可能被召回；
- 必须让 `document_id + version + chunk_index` 可唯一确定一个切片。

关系型向量库中可以按两张主表组织：`knowledge_document` 一行代表一个文档版本，`knowledge_chunk` 一行代表一个切片；`knowledge_chunk` 同时保存正文、`VECTOR(N)` 向量、模型名、维度和过滤元数据。向量列使用近似最近邻索引，正文列保留关键词索引，从而支持向量与 BM25/关键词混合召回。不能把整篇文档的全部向量塞进一个 JSON 字段，否则无法按切片过滤、更新和撤回。

### 6.4.6 云端模型调用链

建议把调用拆成四个独立端口，避免业务代码直接绑定某家 SDK：

```text
DocumentParserPort
  → 提交文件、查询任务、获取结构化块

EmbeddingPort
  → 单条查询向量化、批量切片向量化

RerankerPort
  → query + candidates → 相关性排序

ChatModelPort
  → 依据筛选后的上下文生成受控回答
```

一次完整调用：

```text
Learning 创建入库任务
→ Runtime 调云端文档解析
→ 保存 parser_task_id
→ 轮询或接收回调
→ 获得结构化文档块
→ 服务端切片
→ 批量调云端 Embedding
→ 写向量库
→ 更新 INDEXED

学生提问
→ 调云端 Embedding 生成查询向量
→ 向量库与关键词召回
→ 调云端 Reranker
→ 组装 topK 上下文
→ 调对话模型
→ 返回回答 + 引用
```

调用治理要求：

1. 所有密钥只存在服务端密钥配置中。
2. 每次请求带超时、批次上限、重试上限和幂等键。
3. 批量 Embedding 失败时按批次重试，不把整篇文档重新解析。
4. Reranker 不可用时退回 RRF 融合排序，并标记降级。
5. 文档解析失败时保留原文件和失败原因，允许重新入库。
6. Embedding 模型升级时建立新版本索引，验证后再切换。
7. 记录供应商请求 ID、耗时、token 或字符数、失败码和估算成本。

### 6.4.7 索引版本和原子切换

文档更新不能一边删旧向量一边写新向量，否则切换期间会出现空窗。推荐影子索引：

```text
旧版本 v1 正在服务
→ 构建新版本 v2
→ 校验切片数、向量数、空片率和抽样检索
→ 将“当前读取版本”原子切到 v2
→ 保留 v1 一段时间用于回滚
→ 确认稳定后异步删除 v1
```

撤回资料时：

```text
先将资料标记为不可检索
→ 删除或下线向量版本
→ 校验检索结果已消失
→ 完成业务撤回状态
```

### 6.4.8 检索不是“向量 topK 一步完成”

推荐检索流程：

```text
查询标准化
→ 意图与知识点识别
→ 权限、发布状态、学段、年级、教材过滤
→ 云端查询 Embedding
→ 密集向量召回 30 至 50 条
→ 关键词/BM25 召回 30 至 50 条
→ RRF 融合
→ 云端 Reranker 精排
→ 取 8 至 12 条候选
→ 按父子关系扩展上下文
→ 去重并压缩到 4 至 6 个证据片段
→ 生成回答与引用
```

如果候选为空：

1. 先放宽年级和教材，但仍保留同学段；
2. 再按知识点图谱关联资料查找；
3. 仍为空则拒答或推荐已有课程；
4. 不允许为了“有答案”而退回无关全库。

### 6.4.9 文档质量和 RAG 质量的验收指标

| 阶段 | 指标 |
| --- | --- |
| 文档解析 | 文本覆盖率、OCR 置信度、阅读顺序正确率、表格保留率 |
| 文档清洗 | 页眉页脚去除率、断行修复率、重复段落率 |
| 切片 | 空片率、过短片率、重复片率、标题完整率、表格完整率 |
| 向量入库 | 向量数量一致率、维度正确率、模型版本一致率、幂等成功率 |
| 检索 | Recall@20、Hit@5、MRR、nDCG@10、空结果准确率 |
| 重排 | 人工相关度评分、首条命中率、不同学段串课率 |
| 回答 | 引用准确率、引用覆盖率、事实忠实度、拒答正确率 |
| 工程 | P50/P95 延迟、失败率、重试率、单文档成本、每千次问答成本 |

答辩时最重要的是说明：**RAG 的“准确”不是只看生成答案像不像，而要分别评估解析、切片、召回、重排、引用和忠实度。**

## 6.5 练习、作业和掌握度链路

### AI 小测链路

```text
Agent 生成受控 GAME Artifact
→ Java 保存题目、答案依据和 runId
→ 前端只提交选项、提示次数和作答时长
→ Assessment 校验 runId 属于当前用户
→ Assessment 读取服务端题目并判分
→ 写 assessment_ai_practice_attempt
→ 聚合到 assessment_ai_knowledge_mastery
→ 下一轮 Agent 读取掌握度和薄弱点
```

### 为什么不能在前端判分

如果答案和分数都在浏览器里，学生只要修改 JavaScript 就能伪造成绩。当前做法是浏览器只负责交互，服务端保留题目依据、执行判分并写入过程记录。小学低龄徽章也由服务端判分结果推导，不能通过前端传一个“我完成了”就获得。

### 作业链路

```text
教师创建作业
→ 关联课程和接收学生
→ 录入或批量导入题目
→ 发布
→ 学生作答并提交
→ 客观题自动计分
→ 主观题教师批改
→ 批改历史版本化保存
→ 学生看到分数和反馈
```

### 掌握度怎么理解

掌握度不是“模型凭感觉打分”，而是练习结果的累计统计。当前系统以正确率、练习次数和最近表现为基础，低于 60% 视为薄弱。提示次数和作答时长作为过程证据影响下一步练习策略。它适合做教学决策，但不能宣传成经过大规模心理测量验证的正式能力测评。

## 6.6 知识图谱和个性化推荐链路

### Neo4j 存什么

```text
(知识点A)-[:PREREQUISITE_OF]->(知识点B)
(知识点A)-[:RELATED_TO]->(知识点B)
(课程章节)-[:COVERS]->(知识点)
(教学资料)-[:EXPLAINS]->(知识点)
```

图谱只保存关系和稳定引用键，不复制正文、分数和答案。

### 推荐怎么产生

```text
读取学生近期课程和练习
→ 找到低于阈值的知识点
→ 查询该知识点的先修链
→ 判断先修是否也薄弱
→ 查询哪些已发布章节覆盖目标知识点
→ 生成“补先修”或“学下一节”的候选
→ 附上推荐原因
→ 图谱不可用时回退到已发布课程和确定性规则
```

### 图谱到底改变了什么结果

举一个例子：学生在“先修关系”知识点上只有 45 分。普通系统可能直接推荐更难的后续章节，因为当前页属于那个章节。图谱会发现前置知识点未掌握，推荐“先补先修”，并解释“你对 A 的掌握度为 45%，B 依赖 A”。这就是图谱对业务结果的实际影响，不是只画一张关系图。

## 6.7 多模态和代码沙箱链路

### 当前多模态能力

| 类型 | 当前做法 | 是否完全实时生成 |
| --- | --- | --- |
| 对话 | RAG + 模型 + 确定性降级 | 是 |
| 教学资料 | 教师上传、管理员审核、智能体推荐 | 资源不实时生成 |
| 动画讲解 | 受限步骤 JSON + React 白名单组件 | 是，受控生成 |
| 互动绘本 | 正式数据模型、管理端审核发布、语音朗读 | 绘本以审核资源为主 |
| 编程实践 | Blockly 图形化、Monaco + Python 云沙箱 | 是 |
| 游戏化练习 | 结构化题目、服务端判分、星级或徽章 | 是，题目受控 |

### 为什么不返回任意 HTML/JavaScript

如果模型直接返回一段网页或脚本，前端执行后就可能引入 XSS、恶意跳转、数据泄露和不可控 UI。系统只允许模型返回约定类型的 Artifact，例如 `TEXT`、`ANIMATION`、`GAME`、`CHART`、`IMAGE`。React 只渲染白名单字段，未知类型显示“不可用”。

### 代码执行链路

```text
学生代码
→ Gateway
→ Agent Service 校验角色、代码长度、超时和每日配额
→ 创建平台 runId
→ 同步调用 Runtime，或写入 RabbitMQ
→ Python Worker 调用腾讯云 AGSX
→ 受限 Python 镜像运行
→ stdout、stderr、退出码、耗时和产物标准化
→ 图片/PDF等产物上传 MinIO
→ Java 幂等写回运行状态与 agent_artifact
→ 前端轮询或读取结果
```

### 沙箱安全边界

- 前端不接触云厂商 API Key；
- 用户代码不继承 Runtime 环境变量和云凭证；
- 限制 CPU、内存、执行时长、输出大小、文件大小和产物数量；
- 默认禁止访问互联网，禁止访问业务内网；
- 每次任务使用隔离环境并在结束后销毁；
- 不允许用户任意 `pip install`；
- 云端创建失败与“代码可能已执行”的未知状态分开处理；
- 结果不确定时不自动重复执行，避免副作用。

## 七、高频答辩问题与建议回答

## 7.1 项目定位类

### Q1：请用一句话介绍项目

**答：** 这是一个面向四个 K12 学段的 AI 通识教学助手，用审定知识库、知识图谱和过程性评价，把 AI 讲解、互动练习、掌握度诊断和下一步推荐连成闭环。

### Q2：你们到底解决什么真实问题

**答：** 三个问题：优质 AI 通识教师不足；通用大模型内容不可信；普通学习平台只记录“看过”，不知道怎么解释薄弱点和下一步。我们分别用适龄教学、RAG 引用与拒答、知识图谱和过程证据解决。

### Q3：和 ChatGPT 套壳有什么区别

**答：** ChatGPT 的主要输入是当前问题；我们的输入还包括可信学习档案、课程章节、审核知识、知识点编码、作业成绩、练习过程、先修关系和权限边界。模型只是其中一个环节，系统还会做内容检索、服务端判分、掌握度更新、推荐解释和安全降级。即使模型不可用，我们仍有确定性课程和规则闭环。

### Q4：这和普通网课平台有什么区别

**答：** 普通网课重点是资源播放和进度统计；我们把资源变成可检索知识，把学习行为变成过程证据，再用知识关系解释下一步。课程只是入口，推荐、诊断和反馈才是闭环。

### Q5：系统是不是覆盖所有学科

**答：** 不是。项目目标是 AI 通识教育，不宣称覆盖语文、数学等全部学科。普通学科内容只能作为解释 AI 概念的例子。聚焦范围反而有利于课程质量、知识点编码和评价一致。

### Q6：项目有哪些用户角色

**答：** 学生负责学习和练习；教师负责课程、资料、作业和学生过程证据；管理员负责账号权限、终审、绘本审核、知识图谱和系统治理。同一个系统按权限呈现不同工作台。

### Q7：赛题要求的至少三种多模态，你们完成了几种

**答：** 对话、资料推荐、动画、绘本、编程和游戏化练习都有对应实现。需要说明的是，绘本和文档以审核资源为主，动画和题目是受控结构化生成，不宣传成所有内容都实时生成。

### Q8：项目最有说服力的业务闭环是什么

**答：** 小学低龄“小猫识别”主线：阅读互动绘本，完成图片分类，服务端判分，更新知识点掌握度，获得由记录推导的徽章，再根据图谱或规则推荐下一课。因为它同时覆盖内容、交互、评价、诊断和推荐。

## 7.2 架构与数据类

### Q9：为什么采用微服务，是不是过度设计

**答：** 拆分的核心理由是职责和安全边界，不是追求组件数量。IAM 管身份，Learning 管课程和图谱，Assessment 管评价，Agent 管运行状态，Python 负责模型和工具。这样代码执行、模型调用和教学事务不会混在一个进程里。对比赛部署可以组合部署、减少进程数，但业务边界保留；Nacos 不是核心依赖。

### Q10：为什么 Java 和 Python 都要用

**答：** Java/Spring 更适合 JWT、RBAC、事务、审核状态和业务数据；Python 的 LangGraph、模型 SDK、RAG 和数据处理生态更成熟。Java 是面向学生的业务控制面，Python 是受控执行面，二者通过内部 API Key 隔离。

### Q11：前端为什么不直接调用 Python

**答：** 直连会绕过 JWT、权限、配额、运行审计和产物归属。正确链路必须经过 Gateway 和 Java，由服务端从 JWT 取用户，再创建有归属的运行记录。

### Q12：为什么用这么多数据存储

**答：** 数据形态不同。MySQL 管强事务事实，pgvector 管语义检索，Neo4j 管显式关系，MinIO 管大文件，Redis 管可重建缓存，MongoDB 管运行轨迹，RabbitMQ 管异步消息。不是每个组件都存一份相同数据。

### Q13：MySQL、pgvector、Neo4j 之间怎么保证一致

**答：** 没有跨库分布式事务。用业务状态机、稳定 ID、短事务和补偿控制：资源先进入 `INDEXING`，成功后才标记 `INDEXED`；不确定时标记 `UNKNOWN`；撤回先删向量再完成状态变更；图谱节点使用同一种稳定知识点编码。当前工程能处理正常和可重试失败，但不宣称做到所有跨库场景的强一致。

### Q14：为什么还需要 Neo4j，关系放 MySQL 不行吗

**答：** 简单父子关系可以放 MySQL，但先修链、多跳关系、相关概念和章节覆盖查询更适合图模型。更重要的是图谱改变推荐结果和解释方式，而不是为了换个数据库。

### Q15：Neo4j 和 pgvector 会不会重复

**答：** 不重复。pgvector 回答“哪段正文和问题语义接近”，Neo4j 回答“这些知识点之间谁先谁后、哪一章覆盖它、哪份资料讲解它”。一个偏内容检索，一个偏关系推理。

### Q16：为什么使用 Redis，它挂了怎么办

**答：** Redis 只缓存可重建结果，例如 RAG 检索结果和排行榜。缓存失效时回源到 pgvector 或 MySQL，不影响最终事实。不能把成绩、权限或唯一运行状态只放 Redis。

### Q17：RabbitMQ 挂了会怎样

**答：** 短问答可以继续走同步链路；异步长任务会无法投递，Java 保留运行状态并交由超时任务收敛。系统当前没有事务 Outbox，这是明确的可靠性缺口，不能宣称做到严格恰好一次。

### Q18：Nacos 在项目里起什么作用

**答：** 当前不是主链路。代码里保留服务发现和配置能力，但比赛环境默认使用固定地址。我们不会把 Nacos 当作项目创新或把它画进已运行的核心数据链。

### Q19：系统如何做权限

**答：** 多层控制：Gateway 做 JWT 边界，Spring Security 做 URL 和方法权限，业务服务校验角色与数据归属，Python 内部接口使用内部 API Key。用户 ID 从 JWT 取，跨用户查询统一 404，避免泄露资源是否存在。

### Q20：为什么跨用户查询返回 404 而不是 403

**答：** 403 会暴露“这个 runId 确实存在，只是不属于你”。404 能减少资源枚举和信息泄露。权限审计仍可在服务端记录真实原因。

## 7.3 RAG、大模型与知识质量类

### Q21：为什么一定要 RAG，直接把资料放进 Prompt 不行吗

**答：** 资料规模大时 Prompt 放不下，成本和延迟也高。RAG 先按学段、年级、教材和知识点召回少量内容，再交给模型。这样更可控、可引用、可更新，也更容易在资料撤回后停止使用。

### Q22：RAG 具体怎么检索

**答：** 检索不是简单调用一次向量 topK。正式口径是：先做发布状态、学段、年级、教材和知识点过滤；调用云端 Embedding 生成查询向量；同时做向量召回和关键词召回；用 RRF 融合两路候选；调用云端 Reranker 精排；最后取 8 至 12 条候选，按父子切片补足上下文，去重压缩为 4 至 6 个证据片段交给对话模型。这样同义表达靠向量，人名、术语和编号靠关键词，最终顺序靠 Reranker。

### Q23：文档怎么切分

**答：** 不采用简单固定字符切分。系统先由云端文档解析/OCR 恢复章节、段落、表格、公式和阅读顺序，再做结构感知的递归切片：优先按章节和小节分，其次按自然段和句子边界分。采用父子切片，子片约 300 至 600 个中文字符用于精确召回，父片约 1000 至 1800 个字符用于补全上下文；只在自然段边界保留约 60 至 80 个字符重叠。每个切片都带标题路径、页码、知识点、课程、版本和前后片 ID。

### Q23-1：PDF 从上传到可检索，具体经过哪些步骤

**答：** 文件先做类型、大小、加密和哈希校验，再提交云端文档解析/OCR。云端返回页、标题、段落、表格、公式、图注、坐标和置信度；服务端恢复双栏阅读顺序，清理页眉页脚，修复断行，还原章节层级；然后做结构感知切片和质量门禁，调用云端 Embedding 批量向量化，最后把正文、向量和元数据事务写入向量库，并同步知识图谱资料与知识点的讲解关系。

### Q23-2：切片长度为什么不能固定

**答：** 固定长度不知道语义边界，容易把定义和解释、表格列名和数据、问题和答案拆开。我们的边界优先级是“章节 > 小节 > 自然段 > 句子 > 字符上限”。字符数只是上限，不是切分起点。表格优先整表保留，超大表按行组切并重复列头；公式和图注必须和解释留在同一片。

### Q23-3：文档向量具体怎么存

**答：** 每个切片保存 `document_id + version + chunk_index` 唯一键、正文、向量、父片和前后片 ID、页码、章节路径、知识点编码、课程关系、发布状态、解析器版本、Embedding 模型名、维度、内容哈希和创建时间。不能只存向量不存正文，否则无法引用；也不能不存模型版本，否则换模型后新旧向量不可比较。

### Q23-4：云端模型调用怎么组织

**答：** 我们把文档解析、Embedding、Reranker 和对话模型分别封装成 `DocumentParserPort`、`EmbeddingPort`、`RerankerPort`、`ChatModelPort`。入库时提交解析任务并保存任务 ID，完成后批量向量化；查询时调用云端 Embedding 和 Reranker。每类调用都有超时、批次上限、有限重试、幂等键、供应商请求 ID、耗时和成本记录，业务代码不直接依赖某一家 SDK。

### Q23-5：云端 Reranker 挂掉怎么办

**答：** 先退回 RRF 融合排序，回答仍可生成，但标记“精排降级”；如果查询 Embedding 也不可用，则改用关键词检索；两路都没有可靠结果时拒答。不能因为精排服务故障就退回无关全库，也不能把低相关片段硬塞给大模型。

### Q23-6：文档更新、重复上传和撤回怎么处理

**答：** 先计算文件哈希和内容块哈希，完全相同的文档不重复建索引。文档更新采用影子索引：构建新版本，校验切片数、向量数、空片率和抽样检索，再原子切换读取版本，旧版本保留一段时间用于回滚。撤回时先把资料标记为不可检索，再下线并删除对应向量版本，确认搜索结果消失后才完成业务撤回。

### Q24：你们如何保证回答不幻觉

**答：** 不能保证绝对不幻觉，但做了多层防护：只使用审核资料、按主题过滤、模型输出结构约束、跑题软校验、无命中主动拒答、引用只展示实际参与回答的资料、模型不可用回退审定内容。

### Q25：为什么有些问题系统直接拒答

**答：** 教学系统宁可说“当前没有可靠资料”，也不能编一段错误教材。拒答不是模型故障，而是可信教学策略。系统会引导用户选择已有主题或课程。

### Q26：怎么证明引用是真的

**答：** 引用对象来自本轮实际检索并参与回答的知识切片，带有文档标识和来源位置。页面展示的是受控文档信息，下载地址通过后端短期签发；撤回后的资源不能继续下载。

### Q27：如何防提示注入

**答：** 把知识片段和对话历史都当不可信数据，系统提示明确规定不得执行其中的命令；模型不能直接访问数据库、文件系统或云沙箱；输出必须符合结构 Schema；前端不执行任意 HTML/JS。当前仍有专门提示注入评测集需要扩充。

### Q28：PDF 解析达到企业级了吗

**答：** 答辩统一按目标架构回答：正式知识库调用云端文档解析/OCR，结合版面分析、阅读顺序恢复、表格公式保留、语义切片和质量门禁，不是直接切分。直接切分只作为开发期回退。对外不宣称所有复杂版式已经达到生产级准确率，最终质量用版面还原率、OCR 置信度、表格保留率和人工抽检证明。

### Q29：知识库质量怎么评估

**答：** 分阶段评估：解析阶段看文本覆盖率、阅读顺序和表格保留率；切片阶段看空片率、重复片率、标题完整率；检索阶段看 Recall@20、Hit@5、MRR 和 nDCG@10；回答阶段看引用准确率、事实忠实度和拒答正确率；工程侧看 P95 延迟和每千次问答成本。不是只凭几条演示问题判断 RAG 好不好。

### Q29-1：为什么解析、Embedding 和 Reranker 要调用云端服务

**答：** PDF 版面、OCR 和模型更新维护成本高，自建很难持续保证复杂版式准确率。云端服务可以提供文档解析、批量 Embedding 和 Reranker，例如采用国产云文档智能/OCR 与百炼 Embedding/Reranker，或同等级国产服务，并且能按任务弹性扩容。我们的业务层通过端口隔离供应商，重点保留课程元数据、知识点编码、切片策略、质量门禁和评测集，所以未来可以替换云厂商，而不改教学业务。代价是网络、费用和隐私要求更高，因此必须做超时、降级、成本告警和最小数据外发。

### Q29-2：为什么现在还保留 pgvector，不直接换托管向量库

**答：** pgvector 适合比赛原型和私有化验证，正文、元数据和向量可以在一个 PostgreSQL 事务中维护，部署简单。生产规模扩大后，可以通过 `VectorRepository` 适配到 DashVector 或同等级国产托管向量服务，重点比较过滤能力、召回性能、版本切换、成本和数据合规。选型不是固定绑定某一个库，业务契约保持稳定。

### Q29-3：召回多个片段后怎么交给大模型

**答：** 先按文档、相邻切片和知识点去重，再按父子关系扩展到完整段落，控制在模型的上下文预算内。每个证据片段都保留文档 ID、页码或章节路径，生成时明确区分“参考资料”和“学生问题”。回答完成后只展示真正被使用的引用，避免把检索候选全部伪装成依据。

### Q30：模型换掉会影响系统吗

**答：** 业务层依赖模型的抽象端口，具体千问兼容接口在基础设施适配层。更换模型主要改配置和适配器，但提示词、结构化输出和评测仍需重新验收。

## 7.4 个性化、图谱和教学适配类

### Q31：个性化究竟用了哪些数据

**答：** IAM 的学段、年级、教材和兴趣；Learning 的最近课程进度；Assessment 的近期作业、练习结果、提示次数、耗时和知识点掌握度；Neo4j 的先修关系和章节覆盖；同一会话最近轮次。前端不能伪造画像和成绩。

### Q32：推荐是不是模型随便编的

**答：** 不是。候选由低掌握度知识点、先修缺口和已发布章节覆盖关系生成，模型只负责组织表达。推荐至少带一个可验证原因，例如掌握度低于 60%、先修未掌握或图谱不可用时的规则回退。

### Q33：推荐结果在哪里证明生效

**答：** 同一学生完成小测后，掌握度表和练习过程表发生变化；下一轮 Agent 读取新的掌握度和图谱上下文；成长页推荐课程或下一主题会带原因。现场演示可以连续做一次低分练习，再刷新查看推荐变化。

### Q34：小学和高中是不是只换文案

**答：** 不是。后端按学段选择教学节点、内容深度、检查题和交互产物；小学低龄有专用 Agent 和三阶段短轮次，前端导航、字体、绘本、语音、图片游戏和 Blockly 也不同；高中更强调概念边界、Python、实验和知识引用。

### Q35：同一个知识点怎么体现难度梯度

**答：** 学习目标不同、术语数量不同、例子不同、题目不同、交互不同。例如机器学习：小学通过“教 AI 认猫狗”理解标签，初中理解训练集和测试集，高中理解过拟合、指标和实验设计。

### Q36：系统有长期记忆吗

**答：** 当前有同一 `sessionId` 最近成功轮次的短期对话恢复，以及 MySQL 中的课程、作业、练习和掌握度长期记录。尚未完成跨会话长期摘要、会话列表和完整 LangGraph Checkpointer，不能把短期对话说成永久记忆。

### Q37：为什么不只用大模型做用户画像

**答：** 正式成绩、学段和权限必须可审计。模型可以组织解释，但不能替代数据库中的事实。我们把事实记录和自然语言解释分开，避免模型误改成绩或画像。

## 7.5 多模态与编程类

### Q38：动画是 AI 直接生成视频吗

**答：** 不是。模型生成受控步骤 JSON，前端白名单动画组件按帧渲染。这样可控、可交互、方便暂停和单步，也避免视频生成成本和失败率。实时视频不在比赛阶段范围。

### Q39：绘本是不是 AI 无限生成

**答：** 不是。低龄内容采用正式绘本模型、教师编辑、管理员审核、发布和下架流程，图片和配音存对象存储。AI 可以帮助生产草稿，但不能绕过审核直接推给学生。

### Q40：游戏化练习怎么防止前端作弊

**答：** 题目依据和答案由服务端保存，前端只提交选项、`runId`、提示次数和耗时。Assessment 校验运行归属并判分，掌握度和徽章由数据库结果推导。

### Q41：代码沙箱怎么防恶意代码

**答：** 隔离运行、限制资源、默认禁网、不继承凭证、只允许固定 Python 镜像、限制输出和产物、单用户日配额、云端任务终止和实例销毁。正式使用前还要继续做恶意代码样本和并发配额验收。

### Q42：本地 Piston 和腾讯云是什么关系

**答：** 腾讯云 AGSX 是正式云执行环境，本地 Piston 只用于开发、断网和明确配置的保底演示。它不会变成默认生产方案，也不能在代码可能已经执行后无条件重放。

### Q43：Blockly 和 Scratch 是什么关系

**答：** Blockly 是图形化积木编辑器和代码生成工具，Scratch 是包含舞台、角色、资源社区和运行时的完整产品。我们做的是 Scratch 风格的学习体验，用 Blockly 式积木承载顺序、循环、条件、分类和角色动作，而不是复制 Scratch 的全部生态。

### Q44：为什么不只做 Python

**答：** 小学低龄不适合一上来写代码，图形化更符合认知阶段。初中可以 Blockly/Python 切换，高中突出 Python 实验。平台按学段提供不同实践载体，但后端统一保存任务、过程和结果。

## 7.6 安全、工程和运维类

### Q45：未成年人数据怎么保护

**答：** 只采集教学所需最小数据；身份证、住址、电话等不进入教学上下文；语音以文字和合成朗读为主，不默认保存儿童原始音频；排行榜匿名化；Agent 不诱导填写隐私；不同角色有数据范围；密钥不进入前端和 Git。

### Q46：一个服务故障会不会全站不可用

**答：** 不同依赖按重要性降级。画像或学习历史不可用时，Agent 用最小上下文继续；RAG 不可用时使用审定确定性内容并标记降级；Redis 故障时回源；MinIO 不可用时附件功能不可用但文字课程仍可学；代码沙箱不可用时返回明确状态，不在主进程执行代码。

### Q47：系统瓶颈在哪里

**答：** 大模型、Embedding/Reranker、向量检索和云沙箱是主要外部瓶颈；异步任务还受 Worker 和 RabbitMQ 影响。当前沙箱并发限制是进程级，不能冒充跨实例全局配额，生产化需要分布式限流和监控。

### Q48：你们做了性能测试吗

**答：** 已做过若干真实链路联调和容量手册，但不能宣称生产级压测完成。比如云沙箱有真实成功记录和约 5.6 秒的一次示例耗时，也有不同任务超时样本；这不是 SLA，也不代表高并发能力。

### Q49：为什么没有事务 Outbox

**答：** 这是当前明确的工程边界。Java 先写数据库再投递消息，极端宕机可能导致任务不自动补发，现由超时扫描收敛。后续应增加 Outbox 和 Worker 幂等，才能更强地保证任务不丢且不重复执行。

### Q50：为什么不用 Nacos 做核心卖点

**答：** 评委关心的是教学闭环和可信 AI，不是注册中心数量。Nacos 能优化服务治理，但不直接改善学生学习结果，当前保持延后，避免为了架构名词增加部署复杂度。

## 7.7 创新、壁垒与商业类

### Q51：项目最大的创新是什么

**答：** 不是单独发明某个模型，而是把“学段适配 + 审核 RAG + 知识图谱先修诊断 + 多模态受控产物 + 服务端过程评价”组合成同一条可解释教学闭环。

### Q52：技术壁垒是什么

**答：** 真正的壁垒不是调用大模型，而是四层积累：稳定的知识点与课程数据；审核和索引治理；跨 Java/Python/图谱/向量的可信契约；长期学习过程与教师反馈形成的数据闭环。算法 API 可替换，这些业务资产和工程边界更难短期复制。

### Q53：别人快速抄一个聊天页面怎么办

**答：** 聊天页面不是核心。对方还需要课程知识点编码、审核资料、引用与拒答、服务端判分、掌握度、先修图、教师过程证据和儿童安全边界。单点功能能复制，完整数据链和治理流程不能一天复制。

### Q54：如果迁移到移动云怎么办

**答：** 保持领域接口不变，替换基础设施适配器：模型换兼容 API，对象存储换 S3 兼容服务，代码沙箱换目标云适配器，消息和数据库按目标环境迁移。要重新验收网络、计费、数据出境、密钥和性能，不能只改一个地址。

### Q55：商业上谁愿意付费

**答：** 优先是学校、区域教研机构和培训机构。价值在于降低备课与个性化辅导成本、提供可审计的 AI 教学内容、让教师看到学习过程。比赛阶段没有真实付费数据，不能编造商业验证。

### Q56：最薄弱的环节是什么

**答：** 当前最薄弱的是大规模教学效果证据、企业级 PDF/OCR 质量、长期个性化与安全压力测试。系统功能闭环已形成，但离生产级内容规模和严格 SLA 还有距离，这也是后续路线重点。

### Q57：如果现场只能看一个亮点，看什么

**答：** 看一次小测后推荐是否变化。它把学生作答、服务端判分、掌握度、知识关系和推荐解释串在一起，比单独展示聊天更能说明系统不是套壳。

## 7.8 QPS、高并发与容量类

### Q58：当前项目的 QPS 是多少

**建议回答：**

“我们没有把系统包装成一个脱离业务场景的固定 QPS。当前完成了功能链路、并发边界设计和局部容量验证，但还没有在独立生产环境完成全链路压测，所以不能负责任地报一个‘平台支持多少 QPS’的数字。QPS 必须同时说明具体接口、并发数、机器规格、模型配额、命中率、P95/P99 延迟和错误率。没有这些条件，单独一个 QPS 没有工程意义。”

随后主动补充：

“如果按业务链路拆开看，普通课程读取、缓存命中请求、业务写请求、RAG 问答、异步代码任务是五种完全不同的容量问题。项目下一步会分别压测，而不是用一个聊天接口代表整个平台。”

还要区分 QPS 与 TPS：QPS 是请求吞吐，TPS 更接近完整业务事务吞吐；一次作业提交可能包含多个服务请求，一次异步代码任务也会经历入队、执行和结果回写，不能混成一个数字。

### Q59：为什么不能只给一个总 QPS

**答：** 因为不同接口消耗的资源完全不同：

| 链路 | 主要资源 | 容量特征 |
| --- | --- | --- |
| 健康检查、静态资源 | Gateway、网络、对象存储 | 通常较高，但不代表业务能力 |
| 课程列表、用户资料 | Redis、MySQL、JWT 校验 | 可通过索引和缓存扩展 |
| 选课、提交作业 | MySQL 事务、唯一键和行锁 | 更关注写入一致性，不能只看 QPS |
| RAG 问答 | Embedding、向量检索、Reranker、对话模型 | 通常是最低 QPS 链路，受云模型 RPM/TPM 和长延迟限制 |
| Agent 异步任务 | RabbitMQ、Worker、外部模型 | 入队 QPS 可以高，但完成吞吐受 Worker 和依赖限制 |
| 代码执行 | 云沙箱创建、CPU、运行时长 | 更接近并发任务容量，不等于 HTTP QPS |
| 文件上传下载 | 带宽、MinIO/COS | 受文件大小和出口带宽影响 |

所以正确表述是“某接口在某环境下达到多少 QPS”，而不是“这个微服务项目有固定多少 QPS”。

### Q60：微服务是不是天然支持高并发

**答：** 不是。微服务提供的是可拆分、可横向扩展和故障隔离的基础，不会自动带来高并发。拆分后还增加了网络调用、超时、重试、分布式一致性和链路追踪成本。当前架构的价值是能分别扩展 Gateway、Learning、Agent、Assessment 和 Python Worker，但如果没有压测、连接池治理、限流和容量规划，微服务也可能比单体更慢。

### Q61：当前系统里最可能限制 QPS 的地方在哪里

**答：** 按影响排序：

1. RAG 链路里的云端 Embedding、Reranker 和对话模型，既有网络延迟，也有 RPM/TPM 配额。
2. 代码沙箱的实例创建、运行时长和云平台并发配额。
3. 单实例 Python Runtime 的并发任务和在途请求数。
4. MySQL 写入热点、连接池和慢查询，尤其是提交和掌握度聚合。
5. pgvector 的候选规模、过滤字段和索引命中情况。
6. RabbitMQ 队列积压、Worker 数量和死信处理。
7. Gateway 与 Java 服务本身的线程、连接池和下游超时放大。
8. MinIO/COS 上传下载带宽。

Java 微服务之间的网络调用通常不是第一瓶颈，外部模型与长任务更容易先达到上限。

### Q62：如果评委坚持让你估算一个数量级怎么办

**答：** 不直接编数字，可以给出估算公式和压测计划：

```text
峰值业务 QPS
= 日活用户数
× 峰值时段活跃比例
× 人均每秒请求数

并发请求数
≈ QPS × 平均响应时间
```

例如一次 RAG 问答平均需要数秒，即使系统允许很多连接，真正的稳定吞吐仍会被云端模型配额和响应时间限制。最终应在目标机器和真实模型配额下逐级加压，找到延迟开始非线性上升的拐点。

可以补一句：

“我们现在能讨论的是容量模型和瓶颈顺序，还不能给出经过验收的 QPS 承诺。等压测完成后，会按接口给出 P95、错误率、饱和点和预留余量。”

### Q63：全链路 QPS 应该怎么测

**答：** 用固定环境和固定数据集分四轮：

1. **单服务基线**：分别压 Gateway、IAM、Learning、Assessment、Agent，找到每个服务在没有下游干扰时的上限。
2. **普通业务链路**：登录、课程列表、选课、作业提交，验证 JWT、MySQL、Redis 和连接池。
3. **AI 主链路**：意图识别、Embedding、向量召回、Reranker、模型生成，记录云模型配额和长尾延迟。
4. **异步任务链路**：记录提交 QPS、排队长度、Worker 完成吞吐、任务耗时和失败率。

压测使用 k6、JMeter 或 Gatling 均可，但必须记录：

```text
接口和请求体
机器规格与服务实例数
并发数/虚拟用户数
持续时间和升压曲线
成功 QPS 与总请求 QPS
P50/P95/P99 延迟
HTTP 5xx、业务失败和超时率
CPU、内存、线程、GC、连接池
MySQL QPS、慢查询、锁等待
Redis 命中率和延迟
RabbitMQ 堆积与消费速率
模型 RPM/TPM、重试和限流次数
每千请求成本
```

负载曲线建议从 10、20、50、100 个虚拟用户逐级增加，每一级稳定运行足够时间，再增加突发流量。不能只跑 30 秒就宣称容量。

### Q64：怎样判断压测是否合格

**答：** 先定义 SLO，再看系统是否在 SLO 内稳定，而不是只看最大 QPS。建议把以下条件同时作为合格线：

- 成功率达到目标值，例如 99% 以上；
- P95 延迟满足当前业务场景；
- 错误率随负载上升保持可控；
- CPU、内存、连接池没有持续逼近上限；
- 队列不无限积压；
- 云模型限流和重试不会形成雪崩；
- 连续运行后没有明显内存泄漏和连接泄漏；
- 达到目标容量后仍保留 30% 至 50% 余量。

只要延迟开始非线性上升或错误率快速增加，即使系统还能接收请求，也已经到达实际饱和点。

### Q65：高并发来了以后怎么扩容

**答：** 按瓶颈分层处理：

1. Gateway 和无状态 Java 服务水平扩容。
2. 课程、资料、排行榜等读多写少数据增加 Redis 缓存和短链签名缓存。
3. MySQL 优化索引、连接池、读写分离和热点写入，提交操作继续使用唯一键保证幂等。
4. Agent 和代码任务用 RabbitMQ 削峰，严格限制 Worker 并发，避免无限堆积。
5. RAG 对 Embedding 和 Reranker 设置批量、并发上限、超时和熔断。
6. 模型调用支持流式返回或异步任务，避免一个长请求长期占用 HTTP 线程。
7. 沙箱使用全局限流和排队，不把单进程信号量当成集群容量。
8. 对象存储走短期签名 URL，避免业务服务转发大文件。
9. 加入链路追踪、指标、告警和容量看板，按真实数据扩容。

### Q66：系统现在已经有哪些并发设计

**答：** 已有基础包括：

- Spring Cloud Gateway 统一入口，Java 服务按职责拆分；
- JWT 身份无状态传递，服务端从 Token 取用户；
- Redis 缓存可重建结果；
- RabbitMQ 将智能体和代码长任务异步化；
- Java 运行状态有幂等、超时、取消和终态保护；
- LLM、沙箱和数据库都有超时与错误降级；
- 代码执行有用户日配额，Runtime 有适配器级并发和等待上限；
- MinIO 存大产物，避免数据库成为文件转发中心。

但要明确：这些是并发基础，不是已经验证过的生产容量。

### Q67：当前高并发方面最大的缺口是什么

**答：** 四个缺口：

1. 没有独立环境下的全链路分场景压测，因此没有正式 QPS/SLO 数据。
2. 沙箱和 Runtime 的部分并发限制仍是单进程级，多实例部署后需要全局限流。
3. RabbitMQ 还没有事务 Outbox、Worker 去重和死信重放平台。
4. 缺少完整的链路追踪、容量看板、自动扩缩容和成本告警。

这些是生产化工作，不影响当前答辩主链路，但不能用“微服务”三个字掩盖。

### Q68：高并发时教学系统怎么降级

**答：** 按业务重要性分级降级：

| 级别 | 策略 |
| --- | --- |
| L0 正常 | RAG + Reranker + 模型生成，返回完整引用和互动 |
| L1 精排降级 | Reranker 限流或故障，退回 RRF 融合排序 |
| L2 模型降级 | 对话模型不可用，返回审定确定性讲解和课程推荐 |
| L3 异步削峰 | 长任务返回 `PENDING`，进入 RabbitMQ 排队 |
| L4 最低保障 | 非核心 AI 功能提示繁忙，课程阅读、作业查看和已保存结果继续可用 |

降级不能悄悄发生。响应中要有 `fallbackReason` 或用户可读提示，方便教学人员和运维判断当前答案是否使用了增强能力。

### Q69：现场应答模板

如果评委问“你们 QPS 多少”，建议完整回答：

“当前没有做可对外承诺的全链路压测，所以我不报一个虚的 QPS。架构上我们把链路拆成普通业务、RAG 问答和异步长任务三类：普通业务可以通过 Gateway 和 Java 服务横向扩展；RAG 主要受 Embedding、向量检索、Reranker 和模型 RPM/TPM 约束；代码任务受云沙箱并发和运行时长约束。压测时我们会在固定机器和模型配额下逐级升压，报告成功 QPS、P95/P99、错误率、饱和点和成本。现在可以讨论瓶颈顺序和扩容方案，但不能把未测试的容量说成生产能力。”

如果时间只允许一句：

“微服务提供扩展边界，不等于已经获得高并发；我们的 QPS 要按接口和真实云配额压测后再承诺。”

## 八、压力追问速答

### 1. “你们是不是把大模型包了一层”

不是。请从三处证明：前端不直连模型；回答受审核知识和学段过滤；练习结果会进入 MySQL 并影响下一轮图谱推荐。模型只是执行环节。

### 2. “RAG 是不是只做了向量检索”

不止。还有结构化过滤、关键词候选、重排、引用状态、无命中降级、撤回和缓存失效。当前不宣称所有检索策略都达到企业级规模。

### 3. “图谱是不是摆设”

图谱至少改变两个结果：查询先修缺口，以及按章节覆盖关系生成带原因的下一课。若图谱不可用，系统明确回退到规则推荐。

### 4. “推荐是不是大模型写的”

候选和原因由掌握度、先修关系和章节覆盖产生，模型只负责组织自然语言。这样推荐可以追溯。

### 5. “同一个知识点四学段有什么真正不同”

目标、术语、例子、交互、题目和评价都不同。低龄可能用绘本和图片分类，高中会讲模型边界、指标和 Python 实验，不只是换一段提示词。

### 6. “多智能体为什么不会互相失控”

它们不是无约束自由对话，而是在 LangGraph 受控工作流中按节点执行。每个节点输入输出有协议，跨服务通过固定 API 和内部密钥。

### 7. “为什么不把所有内容交给模型生成”

教学内容需要稳定、审核和可解释。高成本、创造性内容可以受控生成；教材事实、答案、权限和成绩必须来自系统事实源。

### 8. “模型服务挂了怎么办”

回到审定课程和确定性讲解；RAG 故障时标记降级；代码沙箱故障时返回明确错误。不会让主进程直接执行学生代码。

### 9. “代码沙箱能不能绝对安全”

不能承诺绝对安全。我们做了隔离、最小权限、禁网和资源限制，但仍需持续做恶意代码、逃逸、并发和供应商故障测试。安全是边界和验证，不是一句“用了沙箱”。

### 10. “PDF 质量不行怎么办”

正式方案调用云端文档解析/OCR，再结合版面恢复、质量门禁和人工抽检；直接切分只作为开发期回退。复杂表格、公式和低置信度扫描件仍需用真实课程集验证，不宣称未经测试的准确率。

### 11. “没有大用户量，怎么证明能上线”

不虚构用户量。我们提供真实 HTTP 主链路、状态机、权限、降级和容量测试说明作为工程证据，同时明确当前是比赛原型，生产化还需压测、监控和运维验收。

### 12. “为什么还用微服务，单体不是更简单”

单体确实更简单，但代码执行、模型调用、身份和评价需要清晰安全边界。当前保留模块边界，部署时可以减少物理进程；微服务不是评分点，业务闭环才是。

### 13. “Nacos 都没用，架构是不是不完整”

服务发现不是教育产品成立的必要条件。固定地址在比赛环境中更稳定，Nacos 延后是主动取舍，不把未使用组件包装成成果。

### 14. “数据跨库不一致怎么办”

不宣称强一致。通过稳定 ID、状态机、幂等、重试、补偿、人工可恢复状态控制；同时承认 Outbox 和统一分布式事务尚未完成。

### 15. “你们怎么证明学习真的提升了”

目前能证明的是过程闭环和可解释干预，不足以证明大规模学习成绩提升。要形成教育效果证据，需要对照组、前后测、教师评分和长期样本，这是下一阶段研究任务。

### 16. “你们 QPS 多少”

当前没有完成独立生产环境的全链路压测，所以不报虚假总数。普通业务、RAG、异步 Agent 和代码沙箱要分别压测；真正先受限的通常是云端模型配额、向量检索、Worker 和沙箱并发，而不是 Java 服务数量。

### 17. “用了微服务，高并发应该很好吧”

微服务只提供横向扩展和故障隔离的边界，不等于天然高并发。拆分还会带来网络调用和分布式一致性成本。当前已有缓存、消息队列、幂等、超时和限流基础，但没有完成多实例压测和全局配额，不能把架构潜力说成已验证容量。

### 18. “没有压测，怎么证明能支撑高并发”

不能证明最终容量，只能证明系统具备可压测、可扩展和可降级的设计。答辩时说明分场景压测方法、已知瓶颈、扩容顺序和生产化缺口，比报一个没有环境的 QPS 更可信。

## 九、项目亮点怎么讲，避免念技术清单

### 9.1 业务亮点

1. **学段适配贯穿全链路**：不是只改 UI 主题，而是档案、路由、内容、交互、练习和评价一起变化。
2. **AI 教学不是一次性回答**：每次学习会留下进度、练习、提示、耗时和掌握度，后续教学会读取这些事实。
3. **教师始终在回路里**：资料、绘本和正式课程由教师或管理员审核，AI 不替代教材终审。
4. **低龄闭环完整**：绘本、语音、图片分类、服务端判分、徽章和下一课形成可演示主线。
5. **初高中实践能力明确**：Blockly、Python、代码沙箱、图表产物和引用解释适配更高学段。

### 9.2 技术亮点

1. **GraphRAG 分工**：pgvector 找内容，Neo4j 找关系，MySQL 存事实，模型只做受控表达。
2. **可信引用与拒答**：回答能说明依据，没有可靠知识时不编造。
3. **结构化多模态**：模型不返回任意脚本，前端只渲染白名单 Artifact。
4. **安全代码执行**：云沙箱为主、资源受限、产物转存和运行归属可审计。
5. **同步/异步统一**：短问答同步，长任务走 RabbitMQ，有状态、超时、取消和幂等收敛。

### 9.3 工程亮点

1. Java 业务控制面与 Python AI 执行面分离。
2. 用户身份从 JWT 获取，请求体不能伪造 `userId`。
3. 回答上下文优先使用服务端画像，前端只能补充当前交互信息。
4. 资源审核、发布、入库、撤回是状态机，不是几个孤立按钮。
5. 外部依赖故障有业务降级，而不是整条教学链全部失败。

## 十、技术壁垒的准确表述

### 10.1 可以称为壁垒的内容

| 壁垒 | 为什么难复制 |
| --- | --- |
| 四学段课程与知识点体系 | 需要课程专家、稳定编码和长期内容治理 |
| 审核资源到检索引用链路 | 涉及上传、审核、切分、索引、撤回和权限 |
| 学习过程数据模型 | 课程、作业、练习、提示、耗时和掌握度需要统一口径 |
| 图谱与推荐解释 | 先修关系必须可靠，错误关系会误导学生 |
| 安全多模态契约 | 既要可生成，又不能执行任意前端脚本 |
| 受控代码执行链路 | 权限、配额、网络、沙箱、产物和审计必须一起成立 |

### 10.2 不能称为壁垒的内容

- 调用某个大模型 API；
- 写一段 Prompt；
- 使用 LangGraph、Neo4j 或 pgvector 本身；
- 做一个聊天界面；
- 把文件存进 MinIO；
- 用微服务数量证明系统先进。

### 10.3 推荐答辩表述

“我们的壁垒不在单个模型或框架，而在课程知识资产、可信内容治理、跨组件的稳定契约和持续积累的学习过程数据。模型可以替换，但这些数据和闭环不会因为换模型而归零。”

## 十一、几个需要讲出来的设计思考

### 11.1 为什么不是让 AI 接管一切

教育系统要稳定、可解释、可纠错。AI 适合生成解释、组织例子和辅助诊断，不适合单独决定正式成绩、绕过教师审核或执行任意系统操作。系统采用“AI 有边界，教师在回路，数据可追溯”的原则。

### 11.2 为什么要有确定性降级

比赛和大规模教学都不能假设模型永远在线。确定性课程内容能保证基础教学不中断，同时让模型增强成为可选项而不是单点故障。

### 11.3 为什么结构化 JSON 比自由 HTML 更安全

自由 HTML/JS 把执行权交给了模型。结构化 JSON 只传数据，前端决定有哪些组件以及如何渲染。未知字段和未知类型不执行，从设计上缩小攻击面。

### 11.4 为什么过程比一次分数重要

一个学生可能答对但用了很多提示，也可能答错但只差一步。只看分数无法决定怎么教。提示次数、耗时、错误类型和知识点编码能帮助系统选择更合适的下一步。

### 11.5 为什么图谱要经过审核

错误先修关系会长期影响推荐。例如系统错误认定 B 是 A 的先修，学生可能被反复安排无效补课。因此图谱要有目录源、审核状态和稳定编码，不直接让模型自由写正式关系。

### 11.6 为什么不追求“实时生成一切”

实时视频、无限绘本和自由生成教材成本高、延迟长、质量不稳定。比赛阶段优先选择可控、可审核、可交互的方案。技术选择服务于教学，而不是展示模型能生成什么。

## 十四、现场最容易被问倒的六个问题

### 1. “请从点击提交讲到数据库”

**标准回答：** 学生提交答案后，前端只发送选项、提示次数、作答时长和 `runId`。Gateway 校验 JWT，Assessment 根据当前用户查询该 `runId` 的持久化题目和判分依据，在服务端计算得分，写 `assessment_ai_practice_attempt`，再更新 `assessment_ai_knowledge_mastery`，最后返回得分、反馈、徽章和下一步建议。

### 2. “请从教师上传 PDF 讲到 AI 引用”

**标准回答：** 文件进 MinIO，元数据进 MySQL；教师提交，管理员审核发布；管理员触发入库后，Runtime 将文件提交云端文档解析/OCR，拿回页、标题、段落、表格和阅读顺序；服务端清洗并做父子语义切片，再调用云端 Embedding 批量生成向量，把正文、向量、版本和知识点元数据写入 pgvector，同时在 Neo4j 写资料与知识点的 `EXPLAINS` 关系；学生提问时先按学段和知识点混合召回，再调用云端 Reranker 精排，只把实际参与回答的资料作为引用返回。

### 3. “推荐为什么不是随机的”

**标准回答：** 推荐输入是掌握度、先修关系、章节覆盖和发布状态，输出必须附原因。模型只能组织语言，不能凭空创造候选。图谱不可用时才使用确定性规则回退。

### 4. “不同学段为什么不是伪适配”

**标准回答：** 后端有学段路由和专用低龄 Agent，课程活动、练习难度、多模态和前端导航一起变化。请现场对比同一知识点的低龄绘本与高中 Python 实验。

### 5. “AI 出错谁负责”

**标准回答：** 内容先经过审核，回答有引用和拒答，输出经过结构校验，正式成绩不由模型直接决定，教师可查看过程证据并干预。系统还保留审计记录。但没有系统能承诺绝对无错，所以产品设计必须支持发现、撤回和纠错。

### 6. “你项目最难的地方是什么”

**标准回答：** 难的不是调通一个模型，而是让内容审核、RAG、图谱、练习、成绩、推荐和权限在不同服务之间保持同一套稳定编码和状态。只要知识点编码或运行归属错一次，推荐和引用就会失真，所以大量工作花在契约、状态机和降级上。

## 十五、答辩前速记卡

### 15.1 五个关键词

```text
适龄
可信
过程
图谱
闭环
```

### 15.2 五个“不是”

- 不是通用聊天机器人；
- 不是所有内容都实时生成；
- 不是让模型直接决定成绩；
- 不是为了堆中间件；
- 不是已经达到生产级大规模验证。

### 15.3 五个必会数据链

1. 登录 → JWT → 学段档案 → 教学策略。
2. 上传 → 审核 → 发布 → 入库 → pgvector → 引用。
3. 提问 → 意图 → RAG → 讲解 → 引用 → 运行记录。
4. 小测 → 服务端判分 → 练习记录 → 掌握度。
5. 掌握度 → 先修关系 → 推荐原因 → 下一课 → 教师证据。

### 15.4 三句收尾

第一句：**我们不是把大模型接进页面，而是把大模型放进可控的教学流程。**

第二句：**知识库保证“讲得有依据”，知识图谱保证“知道下一步”，过程评价保证“不是只看一次回答”。**

第三句：**当前版本已经形成可运行的教学闭环，下一步重点是内容质量、长期个性化和生产级可靠性，而不是继续堆技术名词。**
