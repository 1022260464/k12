# K12 项目本地部署实测报告

## 1. 测试结论

在当前 16GB Windows 主机上，项目可以完成本地核心基础设施、五个 Java 服务、Python Agent Runtime 和学生端的启动验证。

本次测试采用的运行方式为：

```text
Docker：基础设施
宿主 JVM：IAM、Learning、Assessment、Agent、Gateway
宿主 Python：Agent Runtime
Vite preview：学生端静态产物
```

结论分两层：

1. **当前代码的技术栈可以在这台机器上跑起来。**
2. **当前代码还不能称为最终的“本地最小严格版本完整闭环”**，因为 PostgreSQL 和 MinIO 仍是当前运行依赖；但 MongoDB 已退出默认栈，MinIO 与本地 JSONL 轨迹已完成真实读写验证。

若目标是比赛演示，16GB 内存可行，但必须关闭其他大型应用、限制 JVM 堆，并优先完成阿里巴巴 DashVector + 阿里云 OSS + MySQL RAG 的迁移。若继续保留当前 PostgreSQL 和 MinIO，16GB 会比较紧。

基础设施稳态合计约 **1.45GB**。

数据库初始化检查：

- MySQL 已创建 `k12_auth` 和 `k12_business`。
- `k12_auth` 有 8 张表。
- `k12_business` 有 30 张表。
- PostgreSQL 的 `vector` 扩展版本为 `0.8.0`。
- Neo4j 初始化后有 23 个节点和 30 条关系。

发现并修复一个 Compose 缺陷：

```yaml
healthcheck:
  test: ["CMD-SHELL", "redis-cli -a \"$${REDIS_PASSWORD}\" ping | grep PONG"]
```

原配置使用单引号包住密码变量，容器内不会展开变量，导致 Redis 一直 `WRONGPASS`。修复后 Redis 变为 `healthy`。

## 4. 应用进程验证

对当前源码执行离线 Maven 构建，五个 Java 服务均构建成功。启动时使用以下最大堆限制：

| 服务 | 最大堆 | 健康接口 | 实测工作集 |
| --- | ---: | --- | ---: |
| IAM | 320MB | 200 | 约 109MB |
| Gateway | 256MB | 200 | 约 212MB |
| Learning | 384MB | 200 | 约 262MB |
| Assessment | 384MB | 200 | 约 209MB |
| Agent | 320MB | 200 | 约 226MB |

五个 Java 服务的工作集合计约 **1.02GB**，私有内存合计约 **1.37GB**。

Gateway 到 IAM 的真实 HTTP 路由已验证：

```text
GET http://127.0.0.1:8080/api/v1/iam/health
HTTP 200
```

Python Agent Runtime 在关闭外部写入依赖时可以启动，健康接口返回 `UP`。其工作集约 105MB，但私有内存约 700MB，说明重度依赖导入后的虚拟内存占比较高。后续已单独验证 MinIO与本地 JSONL 轨迹，均不要求启动 MongoDB。

前端验证：

- 学生端 `pnpm build` 成功。
- 管理端 `pnpm build` 成功。
- 学生端生产预览 HTTP 返回 200。
- 两端均存在超过 500KB 的代码分包，不影响演示启动，但后续可以继续拆包。

## 5. 系统内存结果

五个基础设施容器、五个 Java 服务、Python Runtime 同时运行时：

| 指标 | 实测值 |
| --- | ---: |
| Docker 容器内存 | 约 1.45GB |
| 宿主应用工作集 | 约 1.13GB |
| Windows 可用物理内存 | 约 2.6GB 至 3.6GB，采样时受缓存回收影响 |

这组数据不包含：

- MinIO业务规模上传、RAG文档入库和前端媒体回显的峰值
- IDEA 主进程
- 浏览器多个标签页
- 大模型实际问答和文档索引时的峰值

因此当前机器可以演示，但不应同时进行完整镜像构建、大规模 RAG 索引和多个浏览器压测。

## 7. 推荐部署方式

### 当前代码演示

```text
Docker：MySQL、PostgreSQL、Redis、RabbitMQ、Neo4j、MinIO
轨迹：本地 JSONL 文件
IDEA：五个 Java 服务
Python：Agent Runtime
前端：学生端和管理端使用构建后的静态文件
```

16GB 下建议：

- JVM 最大堆控制在 256MB 至 384MB。
- 关闭 Nacos 和 Piston。
- 正式演示使用 `--no-build`。
- 提前构建前端和 Java 产物。
- 只在演示时启动浏览器和 IDEA。
- 不保留其他项目容器。

### 目标最小严格版本

完成迁移后，基础设施应缩减为：

```text
MySQL + Redis + RabbitMQ + Neo4j
```

向量使用 DashVector，对象存储使用阿里云 OSS，MongoDB 轨迹迁移为本地文件或远程日志。该方案更适合 16GB 本机长期演示。

## 8. 最终判断

**16GB 本机可以部署并演示当前项目。MinIO与Agent轨迹文件化已完成真实验收，但完整教学业务和资源迁移仍需继续回归。**

建议先在 122 服务器完成一次完整上传、RAG 问答和业务闭环验证，再回到本机做最小环境演示。比赛前不要继续在同一台 16GB 机器上同时执行全量镜像构建、数据库导入和完整回归。
